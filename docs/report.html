CASE 01High

N+1 query on GET /api/orders

Symptom

Listing orders calls order.getCustomer().getFullName() once per row. Because Order.customer is FetchType.LAZY, that's a separate SELECT … FROM customers WHERE id = ? for every distinct customer touched — one query for the orders, then one more per customer.

Root cause

A lazy association read inside a result-mapping loop, with no batching or fetch strategy declared.

Treatment

Added three alternative endpoints alongside the unoptimized baseline (kept as-is for the case study): a hand-written JOIN FETCH, an @EntityGraph, and a DTO projection that selects only the columns the API returns.

Before4,904 queries1.3–1.6s response
→
After1 query0.08–0.09s response (DTO projection)
−99.98% queries · −94% latency
CASE 02High

Missing index on orders.customer_id

Symptom

Root cause

Composite index (customer_id, created_at DESC) — covers both the equality filter and the sort in one structure.

CASE 03Medium

Offset pagination on large tables

Symptom

GET /api/orders/page uses Spring Data Pageable, executed as ORDER BY id DESC OFFSET ? LIMIT ?. Postgres has to walk and discard every row up to the offset — fine on page 0, costly on the last page.

Root cause

OFFSET cost is O(offset), not O(page size) — it degrades as users page deeper, and gets worse (not better) as the table grows.

Treatment

Keyset (cursor) pagination — WHERE id < :cursor ORDER BY id DESC LIMIT :size. Since id is the primary key, this is an index range scan regardless of depth.

Before · deep page11.701 msSeq Scan + Sort, full table
→
After · same depth0.129 msIndex Scan Backward
−99% at depth · flat regardless of depth
Trade-offKeyset pagination can jump to "next" from a cursor, not to an arbitrary page number — right for infinite scroll and API consumers, wrong for a "jump to page 47" UI.
CASE 04High

Long-held transaction around an external call

Symptom

Order creation is @Transactional end to end, including a simulated ~300ms payment-gateway call. The Hikari connection (pool size 20, intentionally small) sits checked out for the whole thing, payment latency included.

Root cause

A network call unrelated to the database sits inside the same transaction boundary as the writes — a resource meant to be held for milliseconds ends up held for hundreds of them.

Treatment

Took two attempts, and the first one looked right but wasn't. Attempt 1 — split into two short transactions in a separate bean (to dodge Spring's self-invocation trap). Re-benchmarked: no improvement whatsoever — same batching as before. Root cause of that failure: spring.jpa.open-in-view defaults to true and keeps the connection bound to the entire HTTP request, not just inside @Transactional. Attempt 2 — disabled open-in-view. That immediately surfaced a real LazyInitializationException the load test itself caught mid-run, fixed with a targeted Hibernate.initialize() while the session was still open.

Concurrent requestsBeforeAfter
10.48s0.34s
400.80s0.37s
1001.74s0.84s
−52 to −54% at concurrency · batching pattern eliminated
What actually matteredNot "split the transaction" — open-in-view can silently undo that split, and turning it off means auditing every lazy field touched outside a @Transactional method.
CASE 05High

Overselling / race condition on products.stock

Symptom

Stock decrement reads the current value, checks it in Java, then writes a computed absolute value back. Concurrent requests can all read the same pre-decrement stock before any of them commits — Hibernate's UPDATE is a blind overwrite, not a relative expression.

Root cause

No atomicity across the read and the write. Reproduced directly: seeded stock = 10, fired 20 concurrent orders. All 20 read stock = 10, all 20 passed the check, all 20 computed "9" independently — whichever commit landed last simply overwrote the row with its own stale 9.

Treatment

One atomic, conditional statement: UPDATE products SET stock = stock - :qty WHERE id = :id AND stock >= :qty — evaluated against the current committed row, not a stale in-memory value.

Before · stock=10, 20 concurrent20 / 20 oversoldfinal stock: 9 (should be 0)
→
After · same reproduction0 oversold10 fulfilled, 10 × 409 Conflict, final stock: 0
100% over capacity → exactly correct · no added latency
CASE 06Medium

No caching for a hot read path

Symptom

GET /api/products/{id} hits Postgres on every call, even for the same ID requested over and over — a classic hot path (product pages, cart re-reads).

Root cause

No caching layer between the controller and the database.

Treatment

Redis + @Cacheable, JSON serialization (not JDK — stays inspectable via redis-cli), 5-minute TTL.

Before · 50 sequential, same id46–50 queries0.719s total
→
After · cache warm0 queries0.612s total
−100% DB round-trips · −15% latency
Honest readingAgainst a local Postgres already at sub-millisecond query times, request/response and JSON overhead dominate — so the latency win here is modest. The real win is DB load reduction, which would translate into a much larger latency win over a real network-hop database.
CASE 07Medium

Synchronous side effect on order creation

Symptom

A simulated ~250ms order-confirmation notification is sent synchronously, blocking the HTTP response, right after the order is already PAID in the database.

Root cause

A side effect unrelated to the transactional outcome is bolted onto the same request/response cycle as that outcome.

Treatment

Publish an OrderCreatedEvent to Kafka instead — KafkaTemplate.send() enqueues and returns immediately. A separate @KafkaListener sends the notification on its own thread, confirmed via the log timestamp landing after the HTTP response had already returned.

Before · single request0.58s20 concurrent: 0.667s
→
After · single request0.335s20 concurrent: 0.436s
−42% single request · −35% at concurrency
CASE 08High

Thread pool vs. DB connection pool mismatch

Symptom

Tomcat's default 200-thread pool is 10× the intentionally small 20-connection Hikari pool. A burst near thread-pool capacity leaves most threads blocked waiting on Hikari — and /actuator/health, which needs a thread but no DB connection, has to queue behind them.

Root cause

Tomcat's thread pool has no awareness of the connection pool underneath it. Reproduced with ab -n 300 -c 300 — hikaricp.connections.pending confirmed 179–180 threads blocked on the 20-connection pool for roughly the first second of each burst.

Treatment

Moved Actuator to its own port (management.server.port) — its own embedded Tomcat connector, its own thread pool, independent of the app's.

Beforeshared poolhealth check queues behind app traffic
→
Afterisolated poolkept answering + reporting live metrics through every burst
Structural fix — actuator can no longer be starved of a worker thread
Honest readingThe connections-pending metric peaked at ~180 either way (expected — pool size didn't change), and occasional multi-second health-check spikes still occurred after the fix, most likely from JVM-wide GC/JIT pauses a thread-pool split can't isolate. Documented as a real limit, not smoothed over: the verified scope of this fix is thread-pool isolation, not a blanket latency guarantee under load.
CASE 09Medium

Loading full result sets into memory

Symptom

A revenue-by-status report calls findAll(), materializing every row of orders as a full JPA entity just to sum a handful of numbers by status.

Root cause

Aggregating in the application instead of asking the database, which already has an index-aware planner and doesn't need to serialize thousands of objects across the wire.

Treatment

One JPQL query: SELECT o.status, SUM(o.totalAmount), COUNT(o) FROM Order o GROUP BY o.status. Measured allocation via jvm.gc.memory.allocated — a cumulative counter, chosen because raw "heap used" bounced around unpredictably as G1GC reclaimed garbage between measurements.

Before24–46 MBallocated per call · 0.13–0.29s
→
After~0 MBbelow measurable resolution · 0.009–0.013s
10–20× faster · doesn't scale with table size at all
CASE 10Medium

Slow aggregation queries at scale

Symptom

A daily-revenue report filters by created_at, which has no supporting index (only the customer-scoped composite from Case 02). Bulk-loaded 500,000 additional rows (523,501 total) so the date-range filter's selectivity would be realistic.

Root cause

No index for filtering by date range alone — every row has to be read and checked regardless of how small the actual result is.

Treatment

Plain index on orders(created_at).

How this was measured

Every number on this page came from an instrument, not an estimate. Picking the right one — and catching when the wrong one was lying — was half the work.

EXPLAIN ANALYZE

Query plans and real execution times for Cases 02, 03, 10 — repeated 3× where cold buffer cache produced a misleading first reading.

hibernate.generate_statistics

Exact JDBC statement counts for Cases 01 and 06, where the point was query count, not just latency.

Apache Bench (ab)

Single-process concurrent load for Case 08 — switched to it after discovering that spawning hundreds of separate curl processes was itself a source of client-side noise.

jvm.gc.memory.allocated

Cumulative allocation counter for Case 09 — chosen over "heap used," which bounced unpredictably as G1GC reclaimed garbage between reads.

Gatling

Repeatable load-test suite for Cases 03, 06, 10 under real concurrency — run as an isolated Gradle subproject after its Netty version conflicted with Spring Boot's own dependency management.

Prometheus + Grafana

Live dashboard on Hikari pool state, JVM heap, GC pause time, and HTTP latency — the same hikaricp.connections.pending metric that confirmed Case 08's root cause.
